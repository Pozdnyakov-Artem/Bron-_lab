# Техническое руководство БроньЛаб

Рабочий MVP для бронирования общего оборудования одной учебной лаборатории. Создан по бизнес-гипотезе и ТЗ «Этап 2». В одном проекте: адаптивный веб-интерфейс, REST API, Python CLI, SQLite, YAML-конфигурация и тесты.

## Быстрый запуск на Windows

1. Распакуйте архив. Откройте папку `bronylab`.
2. Дважды нажмите `start.cmd`. При первом запуске скрипт создаст `.venv` и установит зависимости; нужен интернет. Требуется Python 3.11+; на этом компьютере доступен также Python из среды Codex.
3. Откройте http://127.0.0.1:8000 в браузере. Оставьте окно запуска открытым. Остановка: Ctrl+C.

Если порт занят, запустите `powershell -ExecutionPolicy Bypass -File start.ps1 -Port 8001`.

### Демонстрационные аккаунты

Все имена, оборудование и аудитории в примере — демонстрационные данные. Самостоятельная регистрация доступна только с почтой @g.nsu.ru; вход для созданного аккаунта — по почте.

| Роль | Логин | Пароль |
|---|---|---|
| Студент | `student-01` | `StudentLab2026!` |
| Преподаватель | `teacher-01` | `TeacherLab2026!` |
| Администратор | `admin-01` | `AdminLab2026!` |

В YAML хранятся хеши, не открытые пароли. Публичные демонстрационные пароли предназначены для локального показа. Перед реальным пилотом замените их командой `set-password` и задайте реальные учётные записи.

## Обычная установка (Windows / Linux / macOS)

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux/macOS:
# source .venv/bin/activate
python -m pip install -e ".[test]"
bronylab validate --config config.yaml
bronylab serve --config config.yaml
```

Вместо `bronylab` можно использовать `python -m bronylab`. Сервер — Waitress, по умолчанию слушает только `127.0.0.1:8000`. Debug отключён. Никакие внешние сервисы для работы приложения не нужны; изображения, стили и скрипты локальные.

## Пользовательский сценарий

Вход → поиск прибора по названию, описанию или аудитории → дата и карточка прибора → просмотр занятости → выбор свободного интервала → подтверждение → «Мои брони».

- Каталог содержит 10 доступных приборов и один скрытый пример. Верхняя статистика показывает число приборов, свободных **весь выбранный день**, и ваших броней на сегодня или последующие даты.
- Расписание автоматически обновляется каждые 15 секунд и при возвращении на вкладку. После бронирования обновляется сразу. Сервер всегда повторно проверяет интервал: данные на экране не дают гарантии до подтверждения.
- Пользователь бронирует только от своего имени. Расписание других пользователей раскрывает только интервалы, без имён и логинов.
- Получение оборудования происходит у сотрудника. Учёт выдачи, SSO, оплата, уведомления и отмена броней не входят в заданные три функции MVP.

## CLI

```bash
bronylab --help
bronylab validate --config config.yaml
bronylab catalog --config config.yaml
bronylab availability --config config.yaml --equipment camera-01 --date 2026-10-06
bronylab run --config examples/batch.yaml --dry-run
bronylab run --config examples/batch.yaml
bronylab set-password --config config.yaml --user student-01
```

`validate` читает и проверяет YAML, не открывая БД и не создавая лог. `run` обрабатывает поле `bookings`; пустой список допустим. `--dry-run` копирует существующую БД в память (или создаёт новую только в памяти), проверяет весь пакет, включая конфликты между его заявками, и записывает план в лог. Файл БД и каталог БД при этом не создаются и не меняются.

Успех: `OK: equipment=10, bookings=2, conflicts=0, skipped=0, errors=0`. При конфликтах или ошибках код завершения 1, при успехе 0; ошибки идут в stderr в формате `ERROR <CODE>: <сообщение>`. CLI выполняется администратором, имеющим доступ к конфигурации и SQLite; публичный доступ к CLI не предоставляется.

**Пакет обрабатывается по порядку, каждая бронь — отдельная транзакция.** При ошибке одной заявки она отклоняется; ранее подтверждённые заявки сохраняются, следующие продолжают обрабатываться. Итог явно показывает частичный результат. Повторный запуск пропускает уже созданные брони; одинаковый ID с другим содержимым отклоняется. Пересечение одного пользователя с его собственной другой бронью также запрещено.

## Конфигурация

```yaml
version: 1
department: "Учебная лаборатория"
timezone: "Asia/Novosibirsk"
work_hours:
  start: "09:00"
  end: "18:00"
database: "data/bronylab.sqlite3"
log_file: "data/bronylab.log"
equipment:
  - id: "camera-01"
    name: "Камера Sony A7"
    location: "Медиакласс, ауд. 312"
    description: "Камера для учебных проектов"
    category: "Камеры"
    status: "available"
admin_users:
  - id: "admin-01"
    name: "Лаборант"
    role: "admin"
users:
  - id: "student-01"
    name: "Студент"
    role: "student"
bookings:
  - id: "request-001"
    equipment_id: "camera-01"
    user_id: "student-01"
    date: "2026-10-06"
    start_time: "10:00"
    end_time: "12:00"
```

После добавления пользователя без `password_hash` задайте пароль через `set-password`; он вводится интерактивно без отображения. Отсутствие пароля не мешает CLI, но запрещает вход в веб-приложение. Повторная загрузка YAML сохраняет пароль, заданный этой командой. Хеш в YAML используется только при первом создании пользователя.

Дополнения к неполному примеру ТЗ: `users` — выдаваемые учётные записи; `password_hash` — начальный хеш Werkzeug; `bookings` — входной пакет CLI; `database`, `log_file`, `timezone`, `department`, `category` — настройки запуска и каталога. Без этих дополнительных полей оригинальный пример ТЗ остаётся валидным. Пути относительно файла YAML, не текущего каталога. Поля `equipment` и `admin_users` могут быть пустыми. Версия и рабочие часы обязательны.

Время строго `HH:MM`, дата — строка в кавычках `YYYY-MM-DD`. Допускаются только один день и рабочие часы; соседние интервалы `10:00–11:00` и `11:00–12:00` совместимы. Минимальный шаг — минута. Новая бронь на дату раньше сегодняшней в часовом поясе подразделения отклоняется с `PAST_DATE` в веб-API, CLI и dry-run. Текущее число проверяется непосредственно перед созданием внутри транзакции, без привязки к часовому поясу браузера. История остаётся доступной, точный повтор уже созданной заявки возвращает SKIP и не создаёт новую запись. Внутри сегодняшнего дня разрешены интервалы в рабочих часах. Лимиты: 30 приборов, 1000 заявок на запуск, конфиг 1 МБ, запрос API 16 КБ. «Мои брони» возвращает до 500 последних записей; история в SQLite сохраняется полностью. Перед запуском пакетного примера замените даты на сегодня или будущие дни.

При изменении YAML перезапустите сервер. Удалённые из YAML приборы скрываются, выданные YAML-пользователи теряют доступ; история броней сохраняется. Созданные на сайте данные не деактивируются этой синхронизацией. Администратор добавляет новые карточки через кнопку «+ Добавить предмет». Начальные приборы можно вносить в YAML. Карточки с source=web и зарегистрированные пользователи сохраняются при синхронизации YAML; синхронизация применяется только к source=config.

## Архитектура и защита от конфликтов

```text
YAML → Config Loader → Repository (SQLite)
                             ↑
Web UI → Flask REST API → BookingService (правила + транзакция)
CLI run → Planner → Executor → BookingService → лог
            └ dry-run: SQLite snapshot в памяти → план → лог
```

Основные модули: `config.py` — загрузчик и правила структуры; `repository.py` — схема и доступ к SQLite; `service.py` — правила времени, план пакетных операций, исполнение и аудит; `web.py` — авторизация и REST; `cli.py` — команды.

`BEGIN IMMEDIATE` сериализует записи перед проверкой пересечения: `old.start < new.end AND old.end > new.start`. Проверка и INSERT находятся в одной транзакции. Дополнительные SQLite-триггеры запрещают пересечения при INSERT и UPDATE даже при обходе сервиса. Ошибка откатывает только текущую операцию. Idempotency: явный ID заявки либо детерминированный хеш прибора, пользователя, даты и времени, плюс проверка точного дубликата.

Студенческие аккаунты создаются регистрацией с доменом @g.nsu.ru (без подтверждения письмом); роль всегда student. Выданные роли задаются через YAML; хеши паролей — scrypt, cookie — HttpOnly/SameSite Strict, CSRF для всех изменений, сессия 8 часов, 5 попыток входа за минуту и 5 попыток регистрации за 15 минут на IP, экранирование текста и Content Security Policy. Лимит входа хранится в памяти одного процесса; для распределённого размещения нужен общий limiter.

Логи — JSON-события в `data/bronylab.log` с суточной UTC-ротацией и максимум 30 архивами; пароли и содержимое сессий не логируются. Удаление старых архивов происходит при ротации. Для строгой очистки при долго остановленном сервисе добавьте системную политику хранения. Веб-ошибки доступа и ошибки операций также записываются.

## REST API

Все ответы JSON. Ошибка: `{"error":{"code":"BOOKING_CONFLICT","message":"..."}}`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/session` | Пользователь, CSRF, рабочие часы, часовой пояс и дата подразделения |
| POST | `/api/login` | `{user_id, password}`; user_id принимает выданный логин или почту; новый CSRF |
| POST | `/api/register` | `{name, email, password, password_confirm}`; только @g.nsu.ru, роль student, вход после регистрации |
| POST | `/api/equipment` | Только admin: `{name, location, category, description}`; 201 с карточкой |
| POST | `/api/logout` | Выход, новый CSRF |
| GET | `/api/equipment` | Доступное оборудование |
| GET | `/api/equipment/<id>/bookings?date=YYYY-MM-DD` | Занятые интервалы |
| GET | `/api/bookings` | Только свои брони |
| POST | `/api/bookings` | `{equipment_id, date, start_time, end_time, id?}` |

Запросы POST передают cookie сессии и `X-CSRF-Token`, полученный из `/api/session`. Новая бронь: 201; уже существующая: 200, action `SKIP`; конфликт: 409; нет входа: 401; нет прав/CSRF: 403; неизвестный или скрытый прибор: 404; ошибка данных: 400; БД: 503.

Коды ТЗ: `CONFIG_NOT_FOUND`, `CONFIG_INVALID`, `INVALID_RULE`, `EQUIPMENT_NOT_FOUND`, `BOOKING_CONFLICT`, `OUTSIDE_WORK_HOURS`, `PERMISSION_DENIED`, `DB_ERROR`. Новые коды: `EMAIL_DOMAIN`, `EMAIL_EXISTS`, `EQUIPMENT_LIMIT`.

## Тесты

```bash
python -m pip install -e ".[test]"
python -m pytest -q
```

106 тестов: валидация YAML и лимитов, некорректные и прошедшие даты, часовой пояс и полночь, рабочие часы, скрытые приборы, права, соседние и пересекающиеся интервалы, идемпотентность, частичный пакет, dry-run с неизменностью байтов базы, ошибки SQLite, сохранение после перезапуска, авторизация, CSRF, приватность, ограничение входа и смена пароля. Тест гонки запускает восемь одновременных соединений: одна бронь подтверждается, семь отклоняются. Время в тестах фиксировано независимо от даты запуска. Дополнительно интерфейс проверен в браузере на размерах desktop/mobile.

## Планировщик

Пример cron (Linux), один и тот же пакет обрабатывается идемпотентно:

```cron
*/15 * * * * cd /opt/bronylab && /opt/bronylab/.venv/bin/bronylab run --config /opt/bronylab/examples/batch.yaml >> /opt/bronylab/data/cron.log 2>&1
```

Замените пути и даты заявок. Cron не отправляет уведомления и не создаёт новые заявки сам: только выполняет подготовленный администратором YAML. На Windows используйте Планировщик заданий: программа `.venv\Scripts\python.exe`, аргументы `-m bronylab run --config C:\путь\bronylab\examples\batch.yaml`.

## Развёртывание пилота и резервная копия

Для своего пилота установите HTTPS на обратном прокси, задайте `BRONYLAB_HTTPS=1`, `BRONYLAB_TRUST_PROXY=1` и постоянный случайный `BRONYLAB_SECRET_KEY` (не менее 32 случайных байтов). В режиме доверенного прокси приложение слушает только `127.0.0.1`; Nginx должен перезаписывать X-Forwarded-For реальным IP клиента. По умолчанию ключ создаётся локально в `data/.session-key`; каталог `data` должен быть доступен только оператору. Доступ к SQLite/YAML/CLI даёт административные права, их нельзя публиковать.

По отдельному поручению владельца приложение размещено на сервере: **https://185.153.183.233:8443/**. Инструкция по управлению и фактическая конфигурация — в `../DEPLOYMENT.md`. Серверные пароли переданы владельцу отдельно; демонстрационные пароли этой инструкции действуют только при локальном запуске.

Для локальной версии: остановите сервис и скопируйте `data/bronylab.sqlite3` и конфигурацию в защищённое место; для копии без остановки используйте SQLite backup API. База в скачиваемом архиве не включена: первый запуск создаёт чистую базу. Запущенная локальная демонстрация может содержать тестовую бронь из проверки интерфейса.

## Решения по неоднозначностям ТЗ

1. В WBS говорится «без сервера, базы данных и сложного интерфейса», но разделы архитектуры и Definition of Done прямо требуют Web UI, API и SQLite. Реализованы эти критерии с одним локальным процессом Waitress.
2. Формат входных заявок CLI и паролей в ТЗ не задан — добавлены описанные выше поля, оригинальная конфигурация сохраняет совместимость.
3. Экран ошибки ТЗ говорит «No bookings were saved». В пакетном режиме более точное поведение: не сохраняется конфликтующая заявка, ранее подтверждённые сохраняются. Статистика это явно отражает.
4. Отдельные внешние действия из PDF (интервью, работа с бюджетным лицом, передача участнику 3) относятся к учебному процессу, не являются поручением отправлять сообщения или размещать проект.

Реализованные критерии готовности и результаты проверок: `../ACCEPTANCE.md`.

Использованная документация: [Flask](https://flask.palletsprojects.com/en/stable/quickstart/), [безопасность Flask](https://flask.palletsprojects.com/en/stable/web-security/), [SQLite в Python](https://docs.python.org/3/library/sqlite3.html).


## Миграция 0.2.0

При старте в users добавляются source (config/web) и уникальный email, в equipment — source. Старые строки считаются config. Изменения выполняются транзакционно; пароли и брони сохраняются. Уникальный индекс email регистронезависимый. Регистрация и добавление предмета используют BEGIN IMMEDIATE, поэтому конкурирующие запросы не обходят уникальность почты и лимит 30 предметов. Перед серверным обновлением создаётся резервная копия SQLite.

Для изменения пользовательского руководства отредактируйте docs/USER_MANUAL.md, затем соберите bronylab/templates/help.html скриптом scripts/build_manual.py (нужен пакет Markdown для сборки, не для работы сайта). Скриншоты лежат в docs/screenshots/manual и bronylab/static/manual/manual.
